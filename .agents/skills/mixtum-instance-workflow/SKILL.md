# Istanza Mixtum

Lavora dal checkout Mixtum indicato dall'utente. Prima di cambiare file, leggi `AGENTS.md`, `templates/instance/README.md` e il piano attivo in `docs/plans/`. Tratta la directory istanza, il suo `.env` e i volumi Docker come dati dell'utente. Non rigenerare credenziali o cancellare volumi per risolvere errori di avvio.

## Nuova istanza

1. Verifica Python 3.12, npm/Node richiesti dalla Console e i comandi già presenti nel repository. Costruisci wheel Platform e dei plugin selezionati in una wheelhouse esterna con `python -m pip wheel --no-deps --wheel-dir WHEELHOUSE .` e, per ogni plugin, il suo `pyproject.toml` (Ticket: `./plugins/ticket`). Non presumere che i pacchetti `0.1.0` siano pubblicati.
2. Usa `bash scripts/create-project.sh /percorso/nuova-istanza` solo su una directory esterna vuota. Il generatore crea `.env` privata e rifiuta destinazioni non vuote. Non mostrare il contenuto di `.env` nei report o nei log.
3. Nell'istanza esegui `make install-wheels WHEELHOUSE=... PYTHON=...`, `make check` e `make wheel-check`. Prima di Docker esegui `make stage-wheels WHEELHOUSE=...`; questa copia i wheel richiesti nell'istanza.
4. Per la Console genera dal checkout `python3 scripts/package-console-bundle.py /percorso/mixtum-console-0.1.0.tar.gz`, poi nell'istanza esegui `make console-build CONSOLE_BUNDLE=/percorso/mixtum-console-0.1.0.tar.gz`. Il bundle contiene i pacchetti frontend inclusi nella release; i pacchetti esterni compilati si aggiungono esplicitamente con il comando descritto sotto.
5. Solo con Docker disponibile e nome progetto/volumi verificati, usa `make prepare` e `make up`. `prepare` costruisce l'immagine, avvia PostgreSQL e Keycloak ed esegue migration esplicite. Verifica `/health/live/`, `/health/ready/`, la Console e l'accesso reale; non dichiarare login o persistenza verificati dal solo `docker compose config`.

Per la prima membership, dopo l'avvio usa nell'istanza `python3 tools/create-local-keycloak-user.py --username alice --email alice@example.test`. La password temporanea è richiesta via TTY; per un agente usa `--password-file` con file privato 0600 ottenuto fuori dalla chat. Il tool opera solo sul Keycloak HTTP in loopback, non concede ruoli o membership e restituisce il `sub`; non usare l'account amministratore bootstrap per la Console. Fai accedere il nuovo utente una volta alla Console per registrare una `ExternalIdentity` da token valido. Poi nell'istanza esegui `docker compose --env-file .env run --rm web python manage.py grant_workspace_member --subject ID --new-workspace-name "Nome"`. Per aggiungere una membership a un workspace esistente, usa `--workspace-id ID`. Non usare email come chiave di collegamento, non elevare l'utente a staff e non scambiare questi comandi per una prova del login reale: verifica poi sessione, selezione workspace e accesso negato agli altri workspace.

## Aggiungere un plugin

Mantieni backend Django e frontend Angular come normali pacchetti, possibilmente in un checkout separato. Per plugin con manifest e metadata nel formato ordinario dello scaffold, nell'istanza usa `make plugin-register PLUGIN_SOURCE=/percorso/plugin`: aggiorna `requirements.txt`, `mixtum_instance/composition.py`, `composition.json` e `console/plugins.ts` dopo controlli statici, senza installare o migrare. Revisiona il diff. Se i punti di composizione sono personalizzati e il comando rifiuta il formato, registra esplicitamente il wheel, il manifest, l'ID e il contributo Console nei medesimi file; non aggirare i controlli cambiando Core. Per un tarball npm compilato e attendibile esegui `make console-add-package CONSOLE_BUNDLE=/percorso/mixtum-console-0.1.0.tar.gz PACKAGE=/percorso/plugin.tgz`, poi versiona `console/vendor/`, `console/package.json` e `console/package-lock.json` generati. `make console-build CONSOLE_BUNDLE=...` usa quei manifest; non occorre modificare il bundle o reinstallare a ogni build. Usa il contratto pubblico `@mixtum/console-api`, non gli internals della Console. Controlla i requisiti del manifest e prova API, route, permessi e workspace. Disabilitare un plugin non deve cancellare tabelle o file; non eseguire migration inverse automatiche.

Per un nuovo plugin usa `python3 scripts/create-plugin.py ID /percorso/nuovo-plugin` soltanto su una destinazione inesistente. Il comando produce file Django/Angular ordinari, una migration iniziale e test workspace-scoped, ma non modifica l'istanza. Leggi il `README.md` generato, adatta il modello al dominio prima di applicare migration e usa `make plugin-register` nell'istanza. Per modificare il frontend con reload locale, usa `make console-dev PLUGIN_SOURCE=/percorso/nuovo-plugin/console` nell'istanza: richiede il checkout Mixtum, collega temporaneamente sorgenti attendibili e non cambia gli artefatti di release. `scripts/verify-external-plugin.py --reload --generated` ne prova il comportamento. Per un plugin reale verifica anche permessi e workspace specifici; non descrivere una registrazione senza pacchetti installati come plugin funzionante.

Per modificare il backend con reload locale, nell'istanza già preparata usa `make plugin-backend-editable PLUGIN_SOURCE=/percorso/nuovo-plugin`, poi `make backend-dev`. Servono gli strumenti di build Python del plugin nel virtualenv; l'installazione editable è solo per sviluppo, mentre la release usa wheel. Verifica il database configurato prima di eseguire migration esplicite: `POSTGRES_HOST=db` funziona nella rete Compose, non necessariamente dal terminale host. `scripts/verify-external-plugin.py --backend-reload --generated` prova il reload su SQLite e checkout temporanei, non su un'istanza cliente.

## Chiusura

Per la prova di recovery locale, `make snapshot-volumes SNAPSHOT_DIR=/percorso/nuovo` richiede istanza completamente ferma e salva i tre volumi locali, non `.env` o S3. `make restore-volumes SNAPSHOT_DIR=/percorso/snapshot-completo` opera solo su un secondo progetto senza container o volumi preesistenti: occorrono la configurazione e le credenziali originali, cambiando soltanto `COMPOSE_PROJECT_NAME`. Non chiamare verificato il recovery finché login, dati e media non sono stati controllati dopo un restore reale. Non cancellare automaticamente volumi parziali in caso di errore.

Riporta quali artefatti e comandi sono stati realmente provati, quali servizi sono partiti, quale database è stato migrato e i gate aperti. Nessun rollout pubblico o `down -v` è implicito in questa skill.
