# Istanza Mixtum locale

Questa directory possiede soltanto composizione, configurazione e personalizzazioni. Il checkout Mixtum indicato da `MIXTUM_SOURCE` in `.env` serve per la build Console da sorgenti durante lo sviluppo; il bundle versionato consente la build senza checkout. Non modificare Core o plugin nel progetto cliente. Il backend si installa dai wheel `0.1.0` dichiarati in `requirements.txt` con il lock `constraints.txt`. **Non è ancora una distribuzione completa pronta per produzione.**

1. `make install-wheels WHEELHOUSE=/percorso/wheelhouse` prepara l'ambiente Python dell'istanza; `make check` verifica il backend installato, senza importare il checkout Mixtum.
2. `make console-build CONSOLE_BUNDLE=/percorso/mixtum-console-0.1.0.tar.gz` compila la Console dal bundle versionato, sovrapponendo `console/plugins.ts`, `console/mixtum-config.json` e `mixtum_instance/composition.json`. Non richiede il checkout sorgente. Senza `CONSOLE_BUNDLE` usa il checkout `MIXTUM_SOURCE` per lo sviluppo. Il risultato generato è in `artifacts/console/browser/`.
3. Costruire i wheel Platform e Ticket in una wheelhouse esterna e lanciare `make stage-wheels WHEELHOUSE=/percorso/wheelhouse` (aggiungere `PYTHON=/percorso/python3.12` se necessario). Con Docker attivo, `make prepare` costruisce il backend dai wheel dell'istanza, avvia PostgreSQL e Keycloak ed esegue le migration una sola volta. Poi `make up` avvia backend e Console. L'immagine backend usa Gunicorn senza bind mount del codice e con utente non-root; per cambiare la composizione bisogna ricostruirla. Database, Keycloak e media usano volumi dedicati; `make stop` non li cancella.

`make prepare` controlla prima che `SECRET_KEY`, `POSTGRES_PASSWORD` e `KEYCLOAK_ADMIN_PASSWORD` siano presenti; una configurazione incompleta non avvia servizi. Le credenziali generate non vengono sovrascritte nelle riesecuzioni. Se il volume PostgreSQL esiste già, recuperare la password originale: cambiare `.env` da solo non la cambia nel database.

Il container `web` riceve soltanto le variabili applicative elencate in `compose.yaml`: la password amministrativa Keycloak rimane fuori dal suo environment. Se un'extension richiede nuove variabili, aggiungile esplicitamente alla composizione dell'istanza; non ripristinare `env_file: [.env]` sul web.

Il backend espone `/health/live/` (processo Django) e `/health/ready/` (connessione al database). Sono endpoint anonimi, non restituiscono dettagli dell'errore e non sostituiscono i controlli di autenticazione o i test applicativi. L'healthcheck dell'immagine usa la readiness.

Per verificare il backend senza importare il checkout sorgente, eseguire `make install-wheels WHEELHOUSE=/percorso/wheelhouse` e `make wheel-check`. Serve Python 3.12; se non è nel PATH come `python3.12`, aggiungere `PYTHON=/percorso/python3.12`. L'immagine backend usa come contesto solo l'istanza e copia esplicitamente file di composizione e wheel: `.env`, il virtualenv e gli artefatti locali non entrano nel contesto. Le dipendenze di terze parti vengono risolte con `constraints.txt` durante la build. Non pubblicare i wheel `0.1.0` come release stabile finché mancano CI e staging.

Il bundle Console `0.1.0` si crea dal checkout di release con `python3 scripts/package-console-bundle.py /percorso/mixtum-console-0.1.0.tar.gz`. Contiene il lockfile, la shell Console e le librerie frontend esplicitamente incluse, non i backend o `node_modules`. La versione è coordinata con i wheel backend. Il bundle non è una release pubblicata né una promessa di compatibilità fra versioni arbitrarie.

Per aggiungere un pacchetto Angular compilato e attendibile senza modificare il bundle o il checkout Mixtum, usa `make console-add-package CONSOLE_BUNDLE=/percorso/mixtum-console-0.1.0.tar.gz PACKAGE=/percorso/plugin.tgz`. Il comando conserva il tarball in `console/vendor/` e genera `console/package.json` e `console/package-lock.json` dell'istanza. Versiona questi tre input: `make console-build CONSOLE_BUNDLE=...` li usa con `npm ci` per una build riproducibile. Il comando installa la dipendenza, ma non abilita una pagina: registra esplicitamente route e navigazione in `console/plugins.ts` tramite il contratto pubblico `@mixtum/console-api`. Per il backend, aggiungi il wheel in `requirements.txt`/`constraints.txt` e la registrazione in `mixtum_instance/composition.py` e `composition.json`. Un plugin incompatibile, non attendibile o privo di queste registrazioni non è un plugin funzionante.

Per un plugin creato dal template o che segue gli stessi metadata ordinari, `make plugin-register PLUGIN_SOURCE=/percorso/checkout-plugin` scrive queste registrazioni nei quattro file dell'istanza dopo aver controllato ID e versioni. Leggi il diff prima di proseguire. Il comando non installa pacchetti, non esegue migration e rifiuta una seconda registrazione; se hai personalizzato il formato dei punti di composizione, registra manualmente. Aggiungi poi il wheel alla wheelhouse e il tarball con `make console-add-package`, quindi verifica check, build, API e permessi.

`tests/fixtures/external_probe/` mostra un plugin minimo con package Python di primo livello, manifest, endpoint workspace-scoped e pagina Angular. `scripts/verify-external-plugin.py` lo copia in un checkout temporaneo distinto e prova wheel/backend e tarball/Console nell'istanza generata. È una prova di composizione, non un plugin di prodotto né un sostituto dei test funzionali del tuo verticale.

Per partire da file modificabili, nel checkout Mixtum esegui `python3 scripts/create-plugin.py customer_portal /percorso/customer-portal`. Il progetto creato contiene un `README.md` con le istruzioni per costruire i due pacchetti. Aggiungi poi wheel, manifest, ID e contribuzione Console ai punti di composizione indicati sopra: lo scaffold non modifica automaticamente un'istanza esistente né ne avvia i servizi.

Durante lo sviluppo frontend, dopo aver registrato la contribuzione del plugin, usa `make console-dev PLUGIN_SOURCE=/percorso/customer-portal/console` nell'istanza. Il comando prepara una Console temporanea, collega il sorgente Angular e avvia il dev server su `127.0.0.1:4200` (`CONSOLE_DEV_PORT=...` per un'altra porta). Una modifica al componente viene ricompilata senza reinstallare il pacchetto; `Ctrl-C` chiude il server. Questo percorso richiede il checkout Mixtum indicato da `MIXTUM_SOURCE` e non cambia i manifest o gli artefatti di rilascio dell'istanza. Usa solo sorgenti plugin attendibili: npm può eseguire script del package.

Durante lo sviluppo backend, dopo aver preparato `.venv` e registrato il manifest del plugin, usa `make plugin-backend-editable PLUGIN_SOURCE=/percorso/customer-portal` e poi `make backend-dev`. Il primo comando installa il package Python in modalità editable nell'ambiente locale dell'istanza; richiede gli strumenti di build Python dichiarati dal plugin e non modifica i wheel di rilascio. Il secondo avvia l'autoreloader Django su `127.0.0.1:8000` (`BACKEND_DEV_PORT=...` per un'altra porta). Le migration rimangono esplicite: esegui `.venv/bin/python manage.py migrate` solo dopo aver verificato quale database indica `.env`. Il valore predefinito `POSTGRES_HOST=db` funziona nella rete Compose, non necessariamente dal terminale host: configura un database di sviluppo raggiungibile prima di lanciare il server. Non usare questo flusso editable in produzione.

Per scegliere i verticali, modifica `mixtum_instance/composition.json`. Le mappe di `mixtum_instance/composition.py` e `console/plugins.ts` sono i normali punti di registrazione esplicita per nuovi plugin o extension. Non inserire segreti nei manifest o nel frontend. Il Public Frontend è facoltativo e non viene creato da questo template.

Il branding globale o di workspace si configura tramite il modello `BrandingSettings` esistente; la Console legge `api/branding/effective/`. La chiave colore legacy `--ed-blue`, se impostata come `#RRGGBB`, determina l'accento della Console e il backend calcola un colore del testo leggibile; valori non validi non vengono applicati come CSS e ricadono sul default. Il logo compatto appare anche al login. Il branding globale è leggibile prima dell'accesso, mentre l'override di workspace richiede membership. Questo non è un editor visuale e non sostituisce la verifica del contrasto e del layout nel browser dell'istanza.

Lo storage S3 è disattivato in `.env` dell'istanza. Se lo abiliti con `USE_S3=1`, configura `AWS_STORAGE_BUCKET_NAME` e prova accesso, permessi e recupero dei file nel tuo ambiente. L'abilitazione non sposta automaticamente i media già presenti nel volume locale; pianifica una migrazione dedicata prima di cambiare storage su un'istanza con dati.

Per creare uno snapshot **cold** dei tre volumi locali, ferma l'intera istanza con `make stop`, poi esegui `make snapshot-volumes SNAPSHOT_DIR=/percorso/assoluto/nuovo-snapshot`. Il comando rifiuta container dell'istanza ancora attivi, volumi mancanti, destinazioni già esistenti e `USE_S3=1`; non ferma servizi né cancella dati. Produce archivi di PostgreSQL, Keycloak e media locali, checksum e `STATUS=complete` solo dopo la verifica degli archivi. Conserva lo snapshot in luogo protetto: contiene dati e file privati. `.env`, configurazione, wheel e bundle Console **non sono inclusi**: custodiscili separatamente, con le credenziali originali. Questo non è ancora un backup completo o una procedura di recovery validata; non usare gli archivi per un ripristino di produzione finché un restore su seconda istanza dedicata non è stato provato. Il comando richiede Docker funzionante e usa l'immagine helper `postgres:16-alpine`.

Per una prova di ripristino, prepara una **seconda directory istanza** con gli stessi file di configurazione, versioni e `.env` originale; cambia soltanto `COMPOSE_PROJECT_NAME` con un nome nuovo. Non usare le credenziali appena generate da `create-project.sh` con un database recuperato. Verifica che il nuovo progetto non abbia container o volumi, quindi dalla seconda istanza esegui `make restore-volumes SNAPSHOT_DIR=/percorso/assoluto/snapshot-completo`. Il comando controlla stato, checksum e percorsi degli archivi prima di creare volumi; rifiuta il progetto sorgente e qualsiasi volume/container già esistente. Se fallisce dopo la creazione di un volume, lo lascia intatto e richiede una verifica manuale: non esegue reset automatici. Non avvia servizi né esegue migration. Prima di `make prepare`/`make up`, conferma che la versione dell'applicazione e le credenziali corrispondano allo snapshot; su staging dedicato verifica login, dati e media. Gli archivi con link o file speciali sono rifiutati: eventuali tablespace PostgreSQL esterni richiedono una procedura specifica. **Il restore reale non è ancora stato eseguito** e il comando non rende l'istanza pronta per produzione.

La prima prova usa Ticket. Il realm locale in `keycloak/realm-mixtum.json` non contiene utenti. Dopo `make prepare` e `make up`, dalla directory istanza usa `python3 tools/create-local-keycloak-user.py --username alice --email alice@example.test`: il comando chiede una password temporanea senza mostrarla e restituisce il `sub`/ID dell'utente creato. Per un agente o un flusso non interattivo, usa `--password-file /percorso/file-privato` con file regolare di proprietà dell'utente e permessi 0600; non inserire password negli argomenti o nel prompt della chat. Il comando accetta soltanto `KEYCLOAK_PUBLIC_URL` HTTP su loopback, non modifica utenti già esistenti e non concede ruoli o workspace. Se la creazione riesce ma l'impostazione della password fallisce, lascia l'utente in Keycloak e segnala l'ID per una correzione manuale; non lo cancella.

Accedi una prima volta alla Console Mixtum con il nuovo utente, non con l'account bootstrap amministratore. Keycloak richiederà il cambio della password temporanea. `/api/workspace/session/` verifica il token e registra l'identità `(issuer, subject)`, ma non concede workspace. Con il `sub` restituito dal comando, esegui `docker compose --env-file .env run --rm web python manage.py grant_workspace_member --subject ID_KEYCLOAK --new-workspace-name "Primo workspace"`. Aggiorna la Console e seleziona il workspace. Per un'identità già verificata e un workspace esistente, usa invece `--workspace-id ID_WORKSPACE`. Per creare un secondo workspace usa `--new-workspace-name "Secondo workspace" --allow-additional-workspace`: senza questa conferma il comando rifiuta la creazione. Il comando rifiuta identità sconosciute, non cerca utenti tramite email e non conferisce privilegi globali. Non eseguirlo per subject non verificati o su database diversi da quello previsto.

In `AUTH_MODE=keycloak` l'URL `/admin/` di Django non è pubblicata: il suo form password locale sarebbe una seconda autenticazione HTTP. Le configurazioni che prima richiedevano l'admin (per esempio aziende e ruoli del Ticket minimo o branding globale) richiedono ancora procedure operative controllate o una futura UI amministrativa con Keycloak; non considerarle self-service nella v0.1. La modalità legacy `AUTH_MODE=django` conserva `/admin/` per la transizione. Non creare un superuser locale nell'istanza Keycloak come scorciatoia per riaprire l'admin.

Il login reale, l'avvio Docker e la prova di snapshot/ripristino restano gate di staging finché non vengono eseguiti. Per un'altra porta/dominio, aggiornare insieme `.env`, `console/mixtum-config.json` e i redirect URI del realm. L'import del realm Keycloak vale per un volume nuovo: modificare il file non aggiorna automaticamente un realm già importato.
