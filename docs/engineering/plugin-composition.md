# Composizione plugin — primo taglio verificato

L'istanza sceglie i plugin, non il Core. L'elenco condiviso della dimostrazione è in `mixtum_instance/composition.json`: `plugins` contiene gli ID abilitati e `capabilities` le capability disponibili. `mixtum_instance/composition.py` associa gli ID ai manifest Python; `MIXTUM_COMPOSITION_MODULE` può indicare un altro modulo importabile per una futura istanza esterna. I manifest dei plugin example e Links non importano modelli Django.

All'avvio il Core valida identificativi, app, prefissi URL, versione dell'API di piattaforma `0.1`, capability e dipendenze tra plugin. Aggiunge le app Django e le URL solo per i plugin selezionati. Con `PLUGINS = ()`, né Example né Links sono caricati o espongono API. Disabilitare un plugin **non** esegue migration inverse e non cancella tabelle o dati; una prova automatica usa un database SQLite temporaneo con dati sentinella per entrambi.

La Console compone route e menu nel file di istanza `console/src/instance/plugins.ts`, filtrando le contribuzioni con gli stessi ID del JSON. Il plugin example fornisce sorgenti Angular in `plugins/plugin_example/console/src/` come pacchetto locale `@mixtum/plugin-example-console`; importa solo il contratto pubblico `@mixtum/console-api` per route, navigazione, URL API e workspace selezionato. L'interceptor e l'autorizzazione server-side restano responsabilità della piattaforma. La pagina del plugin gestisce workspace non selezionato, caricamento, elenco vuoto, errore e accesso negato.

Per sviluppare, eseguire una volta `cd console && npm ci`, poi `npm start`. Il pacchetto locale è collegato da npm: una modifica ai suoi sorgenti non richiede una nuova installazione. Il comando `start` usa polling a 1000 ms e disabilita il prebundling del pacchetto TS locale: in questa configurazione macOS il watcher predefinito esaurisce i file descriptor e il prebundling non risolve gli import TS interni. La prova ha osservato ricompilazione e page reload dopo una modifica del componente, senza reinstallazione; il browser autenticato non è stato verificato perché Keycloak non era disponibile.

Per produrre gli artefatti compilati, dopo `npm ci` in `console/`, eseguire `npm run build:plugin-packages`. Il comando usa `ng-packagr` in modalità Angular partial e genera `dist/` in entrambi i pacchetti. Da ciascuna directory `dist/` si può eseguire `npm pack`: i tarball contengono FESM e dichiarazioni TypeScript, non i sorgenti dell'applicazione. I due pacchetti restano `private` per evitare pubblicazioni accidentali: un'eventuale pubblicazione su registry richiederà una decisione esplicita. I peer Angular e `rxjs` devono essere forniti dalla Console consumatrice; il plugin richiede anche `@mixtum/console-api@0.1.0`.

La compilazione dei due pacchetti, la creazione dei tarball, la loro installazione temporanea nella Console e la build del consumer con il chunk lazy compilato sono state verificate. In questo host macOS `ng build` termina con exit 134 nel sandbox, anche con i pacchetti sorgente; la stessa build riesce fuori dal sandbox. Dopo la prova il lockfile è stato ripristinato con `npm ci`.

Il backend example ha un `pyproject.toml` nel proprio checkout. Da `plugins/plugin_example/`, `python -m pip wheel --no-deps .` produce un wheel con `plugins.plugin_example` e la migration originale, senza includere i test. Un sdist autonomo è stato ricostruito in wheel. Il package padre `plugins` nel checkout usa `pkgutil.extend_path` per mantenere la discovery standard dei test Django e importare plugin installati in altri percorsi Python. La composizione rimane esplicita: installare il wheel non abilita il plugin né esegue migration. Il wheel presuppone che l'istanza fornisca Core, workspace e identity Mixtum; non è un'applicazione Django autonoma.

Lo stesso backend example è stato verificato in una istanza tecnica temporanea senza copia locale del plugin: un `django check` carica prima il checkout separato, poi il wheel installato, mantenendo app label e URL. Un'ulteriore prova ha installato il checkout Python in modalità editable in una venv temporanea e verificato l'import da quel checkout. Il test automatico copre il caricamento del checkout esterno; questa prova non equivale ancora a un template cliente completo. I 15 test placeholder del plugin sono stati sostituiti con asserzioni reali su scope e API.

Anche il frontend è stato provato dal medesimo checkout esterno: `npm install --no-save --package-lock=false <checkout>/plugins/plugin_example/console` nella Console collega il pacchetto senza modificare i manifest, poi `npm run build` e i 7 test ChromeHeadless passano. Con `npm start` su loopback, una modifica al componente nel checkout esterno ha ricompilato il chunk lazy e inviato `Component update sent to client(s)` senza reinstallazione; il file è stato ripristinato e `npm ci` ha riportato la Console alla dipendenza locale del lockfile. Per un'istanza reale, il percorso o la versione del pacchetto va invece dichiarato nel manifest dell'istanza e bloccato nel lockfile; `--no-save` è solo una prova temporanea.

Links è ora il secondo caso indipendente: app label e tabella storiche restano stabili, ma la nuova API e la pagina Console sono workspace-scoped. La migration additiva conserva e nasconde i record legacy senza workspace; vedere [la procedura Links](links-transition.md) per rilascio e recovery. Un'istanza tecnica senza sorgenti plugin nel proprio `plugins/` ha importato Example e Links da due wheel installati; `django check` e le URL sono stati verificati. I tre tarball Angular compilati (contratto pubblico e due plugin) sono stati installati temporaneamente insieme nella Console e la build ha prodotto due chunk lazy; poi `npm ci` ha ripristinato i sorgenti locali. Restano Ticket minimo, extension e composizione cliente completa. Il CI è configurato per costruire wheel e pacchetti Angular, ma il workflow non è ancora stato osservato su un runner.

Il Dockerfile Console usa Node 22.22.3 e include le directory dei pacchetti locali prima di `npm ci`, poi copia soltanto `dist/adr-payment-hub/browser` nell'immagine Nginx. La configurazione Compose è validata staticamente; l'immagine non è stata costruita in questa fase perché il daemon Docker locale non risponde. L'URL runtime dell'esempio è locale e non configura ancora un deployment pubblico.
